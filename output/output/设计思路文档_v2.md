# 全栈开发 Agent 团队 —— 设计思路文档（v2）

> 本版相对初稿的主要变化：存储从 SQLite 改为**纯 JSON 文件**、前端 CSS 改为**系统注入**、
> **QA 自动修复循环**与**运行时冒烟测试**从"未来工作"落地为已实现，新增**一键启动器**。
> 文末新增「实现思路历程与踩坑记录」和更新后的「Future Work」。

---

## 一、项目概述

本项目实现了一个"全栈开发 Agent 团队"系统：用户只需输入一句话需求（如"帮我做一个待办事项 Web 应用"），系统通过多个 AI Agent 协作，自动产出一个**完整、可运行、零原生依赖**的 Web 项目，包括前端代码、后端代码、本地数据存储、README 及启动脚本。

核心设计理念有三条：

1. **不是一个超大单 Agent 一把梭，而是多个职责分明的 Agent 组成团队，按流水线协作。**
2. **不只生成，还要验证并自我修复**：QA Agent 用确定性检查 + 真实运行时冒烟测试守底线，发现问题后流水线会自动重跑相关 Agent，最多 3 轮，形成闭环。

## 二、系统架构总览

### 2.1 Agent 团队成员与职责边界

系统由 6 个 Agent 组成，每个 Agent 有清晰的职责边界，只做自己该做的事：

| Agent | 角色 | 职责 | 产出物 |
|-------|------|------|--------|
| **ProductManager** | 产品经理 | 把模糊需求转化为结构化 PRD | PRD（JSON） |
| **Architect** | 架构师 | 基于 PRD 设计技术方案和 API 契约 | 技术架构 + API Contract + 数据模型 |
| **Backend** | 后端工程师 | 按 API 契约实现后端代码 | `server.js`、`db.js`、`package.json` |
| **Frontend** | 前端工程师 | 按 API 契约实现前端页面 | `index.html`、`app.js`（`styles.css` 由系统注入） |
| **DevOps** | 运维工程师 | 生成工程化交付文件 | `README.md`、`start.sh`、`.gitignore` |
| **QA** | 测试工程师 | 静态检查 + 契约一致性 + **运行时冒烟** | QA 质检报告 |

### 2.2 流水线执行顺序

```
用户需求 → PM → Architect → Backend → Frontend → DevOps → QA → 可运行项目
```

这是一条**严格的串行流水线**，每个 Agent 依赖上游 Agent 的产出。

v2.0版本末端多了一个**修复回边**：QA 不通过时，编排器会把失败项映射到具体 Agent 并重跑，直到全绿或达到轮次上限。

- PM 的 PRD 是所有后续 Agent 的需求基础。
- Architect 的 API Contract 是前后端的"合同"，确保两端不打架。
- Backend 和 Frontend 严格按照 Contract 实现，不能自行增减接口。
- QA 在最后做交叉验证与真实运行验证，不通过则触发自动修复。

### 2.3 关键技术选型与设计决策

**为什么放弃 SQLite，改用本地 JSON 文件存储？（本版重大变更）**

初稿用的是 SQLite。但 SQLite 系的 Node 驱动（`better-sqlite3` / `sqlite3`）大多是**原生模块**，`npm install` 时要走 `node-gyp` 现场编译，在很多机器上会因缺少编译工具链而失败，或拖慢安装。这直接破坏了"零配置、一键启动"的目标。

新版改为：后端只用 Node 内置 `fs` 读写一个 `data.json`，`db.js` 负责 `load()` / `save()`，文件不存在时返回按 `data_models` 生成的初始结构（每个集合一个空数组 + 一个自增计数器 `seq`）。代价是没有事务与并发控制，但对 hello-world MVP 完全够用，换来的是 `npm install` 只拉 `express` + `cors`，**秒过、零编译**。架构师 Prompt 里因此明令禁止任何数据库驱动。

**为什么前端 CSS 不经过 LLM，而由系统直接注入？（本版重大变更）**

让 LLM 在一个多文件 JSON 里把整张样式表当字符串值输出，转义极易出问题（换行、引号、URL 里的斜杠），CSS 经常被截断或损坏。新版把一套现代、克制、自带浅色/深色主题的 `BASE_CSS` 固定写在 `frontend_dev.py` 里，**直接注入，不经过 LLM**，因此永不丢失、永不出错。前端 Agent 只需产出 `index.html` 和 `app.js`，并使用约定好的类名。若模型仍附带了 CSS，则追加在注入主题之后，不覆盖。

**为什么 QA 用确定性检查 + 真实运行，而不是再问一次 LLM？**

QA 是系统的"刹车"，目的是拦住 LLM 幻觉。如果再调一次 LLM 去判断"代码对不对"，既不可靠又要把全部代码塞进上下文（加剧上下文膨胀）。所以 QA 几乎全部用确定性手段：正则匹配、JSON 解析、`node --check`、以及真正把服务跑起来打接口。确定性检查对 token 的消耗为零，结论可复现。

**为什么仍然串行，而非并行 Backend 和 Frontend？**

真正让前后端"不打架"的是 **API Contract**——Frontend 在写代码时**并不阅读 Backend 生成的代码**，只阅读契约（见 3.3）。因此并行在正确性上其实是可行的。当前选择串行，主要是为了实现简单、执行确定、产物落盘顺序清晰，并保留"下游可参考上游文件清单"的余地。并行化留作 Future Work。

## 三、Agent 间通信机制

### 3.1 共享上下文 —— "黑板模式"（Blackboard Pattern）

Agent 之间**不直接通信**，而是通过一个共享的 `SharedContext` 对象读写数据：

```
SharedContext（黑板）
├── requirement      ← 用户原始需求
├── prd              ← PM 写入，Architect/Backend/Frontend 读取
├── architecture     ← Architect 写入，Backend/Frontend/QA 读取
│   └── api_contract ← 核心！前后端的"单一事实源"
├── backend_files    ← Backend 写入，DevOps/QA 读取
├── frontend_files   ← Frontend 写入（styles.css 由系统注入后并入），DevOps/QA 读取
├── devops_files     ← DevOps 写入
├── qa_report        ← QA 写入
├── qa_failures      ← 【本版新增】上一轮 QA 未通过的 check 列表，修复轮专用
└── history          ← 所有 Agent 的活动日志
```

### 3.2 为什么用黑板模式而非消息传递？

- **解耦**：Agent 之间无直接依赖，新增 Agent 只需读写黑板上的字段。
- **可审计**：每次写入都落盘到 `_agent_artifacts/` 目录，可回溯每个 Agent 的输入输出。
- **可断点续跑**：理论上可从中间某个 Agent 重新开始（中间产物都在磁盘上）。
- **避免互相打架**：每个 Agent 只写自己的字段、读别人的字段，不会互相覆盖。

### 3.3 上下文裁剪 —— `summary_for()` 与"契约即压缩边界"

这是本版**特别值得强调**的机制，也是把整套系统压进一个小上下文窗口（见 5.2）的关键。

`summary_for(agent_name)` 并不把黑板上的全部内容丢给每个 Agent，而是只暴露下游需要的字段。它实际暴露的是：**用户需求 + PRD + 技术架构（含 api_contract）**，外加修复轮的失败项——但**从不把上游生成的代码本身塞进 prompt**。

这一点的精妙之处在于：**API Contract 充当了一道压缩边界。** 与其把 Backend 生成的几百行 `server.js` 喂给 Frontend，不如只喂那份契约——契约就是"Backend 对外行为"的压缩表示。这样每个 Agent 的 prompt 体量大致是 `|PRD| + |architecture|` 的量级，**与上游已经生成了多少代码无关**。这是控制上下文膨胀的核心抓手。

好处：

- **token 可控**：无论生成多少代码，下游 prompt 不随之线性膨胀。
- **避免无关信息干扰**：模型只看接口，不被实现细节带偏。
- **遵循最小权限原则**：每个 Agent 只看自己该看的。

### 3.4 API Contract —— 前后端的"合同"

这是整个系统中最关键的协调机制。Architect 产出的 `api_contract` 定义了每个接口的 `method`、`path`、请求体和响应体。Backend 和 Frontend 都必须严格遵守：

- **Backend**：只能实现 Contract 中声明的接口，不能增也不能减。
- **Frontend**：只能调用 Contract 中声明的接口，不能调用未声明的；同时**必须把每个接口都用上**（见 4.1 覆盖率检查）。

QA 会在最后双向验证这份一致性，形成闭环。

## 四、质量保障机制

### 4.1 QA Agent 的十项确定性检查

QA 大量使用确定性检查（正则、JSON 解析、文件存在性、子进程），而非再调一次 LLM：

| # | 检查项 | 检查方式 | 目的 |
|---|--------|----------|------|
| 1 | 架构声明的文件全部生成 | 文件列表比对（归一化 `public/` 前缀） | 防漏 |
| 2 | `package.json` 合法且有 start 脚本 | JSON 解析 | 确保可启动 |
| 3 | 后端实现了 Contract 全部接口 | 正则匹配 `app.get/post/...` | 防 Backend 漏接口 |
| 4 | 前端只调用 Contract 中的接口 | 正则提取 `fetch()` + **路径归一化**比对 | 防越界调用 |
| 5 | **前端实现了 Contract 的每一种操作** | 按 HTTP 方法反向核对覆盖率 | **防 Frontend 漏做删/改/标记完成** |
| 6 | **`index.html` 以合法 `<!DOCTYPE html>` 开头** | 字符串前缀检查 | 拦 `<!--DOCTYPE`（漏感叹号）整页解析异常 |
| 7 | **后端用 `express.static` 托管前端** | 正则匹配 | 防访问 `/` 时 `Cannot GET /` |
| 8 | JS 语法检查 | `node --check`（utf-8 解码） | 防语法错误 |
| 9 | **运行时冒烟测试** | 真 `npm install` + 启动 + 打接口 | **拦"语法对但跑不起来"** |
| 10 | 工程化文件齐全 | 文件存在性 | 确保可交付 |


### 4.2 运行时冒烟测试 —— 唯一能拦"语法对但跑不起来"的手段（本版新增）

`node --check` 只能查语法，查不出"语法没错但一启动就崩 / 一访问就 404"。第 9 项检查真正把项目跑起来：

1. `npm install`（超时 300s 即判失败）；
2. 选一个空闲随机端口，`node server.js` 启动服务；
3. 在 12s 内轮询就绪；若进程提前退出，判定"启动即崩溃"并回传 stderr 末几行；
4. `GET /` —— 验证静态托管（拿不到 HTML 多半是缺 `express.static`）；
5. `GET <契约里第一个集合级接口>` —— 验证读链路；
6. `POST <契约里第一个 POST>` —— 验证写链路，请求体从契约示例或 `data_models` 合成。

**通用性**：探测哪些接口、用什么请求体，全部从 `api_contract` / `data_models` 推断，不写死任何业务路径，因此对任意项目都适用。**容错口径**：4xx（校验未过 / 资源不存在）视为正常应用行为，只有启动崩溃、缺静态、5xx 才判失败。本机若无 node/npm，则跳过该项（判通过）。

### 4.3 自动修复循环 Fix Loop（本2.0版新增，初稿列为未来工作）

编排器在 QA 之后进入最多 `MAX_QA_ROUNDS = 3` 轮的循环：

1. 把当前所有文件落盘（QA 的语法/冒烟检查依赖磁盘文件）。
2. 跑 QA；若 `all_passed` 则提前退出。
3. 否则用 `_get_failed_agents()` 把失败项**映射到具体 Agent**（`{Backend, Frontend, DevOps}` 的子集）。例如：缺 `server.js`/契约接口未实现/缺 `express.static`/冒烟启动失败 → Backend；缺前端操作/`fetch` 越界/`<!DOCTYPE>` 不对 → Frontend；缺工程化文件 → DevOps。
4. 把失败项写入 `ctx.qa_failures`，`summary_for()` 会**把这份失败清单作为 delta 注入**到被重跑 Agent 的 prompt，要求逐条修复。
5. 重跑相关 Agent 后**清空 `qa_failures`**，防止过期数据污染后续正常轮次。

只重跑"出问题的人"而非整条流水线，既省调用，也避免把已正确的产物推翻重来。

### 4.4 LLM 输出可靠性保障

- **JSON Mode**：调用 LLM 时启用 `response_format: json_object`，强制 JSON 输出。
- **区分可重试与致命错误**：`JSONDecodeError`（格式错）→ 带错误反馈重试，最多 3 次让模型自我修正；其他 `Exception`（404/401/连接拒绝等 API 级错误）→ **立即抛出并附诊断信息**，不浪费重试次数（详见 5.10）。
- **代码围栏兜底**：部分模型即使在 JSON Mode 下仍会用 ```` ```json ```` 包裹，`_strip_code_fence()` 做兜底清理。
- **中间产物全落盘**：每个 Agent 的 prompt 和 output 都存到 `_agent_artifacts/`，便于人工审计和问题定位。

### 4.5 人工介入机制（Human-in-the-Loop）

在两个关键决策点支持人工审核：(1) PRD 产出后，确认需求理解；(2) 架构方案产出后，确认技术方案。通过 `--interactive` 或 `HUMAN_IN_LOOP=true` 开启。审核不通过则流水线直接中止，避免在错误方向上浪费后续 Agent 调用。

## 五、实现思路历程与踩坑记录

这一章记录从想法到能跑的真实推演路径，以及一路踩到的坑和对应的工程取舍——很多设计决策是被现实"逼"出来的。

### 5.1 起点：从"单 Agent 一把梭"到"流水线分工"

直接让一个模型"读需求 → 一次性吐出整个项目"。问题很明显：单次输出太长、模型容易在中途"忘记"前面的约束（接口对不上、前后端字段不一致、文件互相矛盾），而且产物一旦出错很难定位是哪个环节的锅。于是采用**职责分明的流水线**：PM 只澄清需求、Architect 只定契约、Backend/Frontend 各写一端、DevOps 收尾、QA 把关。每个环节产物更短、更聚焦，也天然可审计、可断点。

### 5.2 本地小模型的硬约束：显卡不足 → 把上下文窗口压到 8k

开发主要在本地用 Ollama 跑 `qwen-coder` 7B 级别的模型。第一道现实墙是**显存**：把上下文窗口开到 16k 时，KV cache 撑得很大、解码变慢，单次请求经常**超时**（`LLM_TIMEOUT` 已放到 600s 仍不稳）。把窗口降到 **8k** 后才能稳定跑完——`LLM_MODEL` 默认就叫 `qwen-coder-8k`，正是这个权衡的产物。

但 8k 窗口意味着**输入 prompt + 输出补全必须共享这点预算**，几乎没有冗余空间。这条硬约束直接决定了后面一连串"省 token"的设计——也就是 5.3。

### 5.3 上下文膨胀治理：把每个 Agent 的 prompt 摁在窗口里

流水线最容易犯的错是"把累积的全部上下文都丢给下一个 Agent"——到 Frontend/QA 时，上下文 = 需求 + PRD + 架构 + 后端全部代码 + 前端全部代码……轻松爆掉 8k。主要用了五条互补策略把它摁住：

1. **契约即压缩边界（最关键）**：下游 Agent 永远只拿到结构化的**契约**（PRD + architecture），**从不拿上游生成的代码**。契约是"上游对外行为"的浓缩，体量恒定，与生成了多少代码无关（见 3.3）。
2. **CSS 移出 LLM**：把整张样式表（约 2KB）从输入和输出里彻底拿掉，由系统注入。模型既不用读它也不用写它。
3. **确定性 QA，不再过 LLM**：QA 用正则/JSON/子进程判断，对上下文的占用为零；否则"让 LLM 审代码"就得把全部代码塞回窗口。
4. **修复轮只注入 delta**：修复时不重发全部上下文，只把**失败项清单**追加进 prompt，且用完即清空。
5. **极简技术栈顺带也压缩了 prompt**：JSON 文件存储没有建表 DDL、没有迁移、没有 ORM 模板要描述，数据模型只是几行字段列表，prompt 自然更短。

### 5.4 LLM 多文件 JSON 输出的"转义地狱"

让模型在一个 JSON 里把多份文件当字符串值输出，转义是重灾区：CSS/HTML/JS 里的换行、引号、正则字面量的斜杠都会破坏 JSON。对策有两层：

- **能不让模型写的就别让它写**：CSS 直接注入（5.3 第 2 条）。
- **必须让它写的就约束写法**：前端 Prompt 明确要求——HTML 一律用**模板字符串（反引号）+ 单引号属性**，**绝不用单引号字符串跨行拼接**（会直接 `SyntaxError`），**不写正则字面量**（要正则就 `new RegExp("...")`），只用 ASCII 引号。这些都是为了让生成的代码对 JSON 转义友好、对 `node --check` 友好。

### 5.5 放弃 SQLite：原生编译之痛 → 纯 `fs` JSON

初稿的 SQLite 方案在"一键启动"上栽了跟头：`better-sqlite3` 之类要现场编译原生模块，换台机器、缺工具链就 `npm install` 失败或巨慢。彻底改为 Node 内置 `fs` 读写 `data.json`：`db.js` 负责 `load/save`，文件不存在时按 `data_models` 返回初始结构并维护自增 `seq`。代价是无事务/并发，但 MVP 够用，换来"零编译、秒装"。架构师与后端 Prompt 都把数据库驱动列入黑名单，从源头杜绝模型"好心"引入。

### 5.6 QA 自己的 bug 反而逼坏了产物：路径归一化

这是最有意思的一个坑。早期 QA 的"前端越界调用"检查，只把**契约里**的 `:id` 归一化成 `:param`，却没处理契约实际使用的 **`{id}`**（OpenAPI 写法）。结果所有带参接口（删除、更新、标记完成）都被误判为"契约里没有、属于越界"。模型为了通过 QA，**干脆把删/改/标记完成的 `fetch` 全删掉**——于是"功能缺失"成了系统性现象，而且看起来还全绿。

教训：**检查器本身的 bug 会通过"为过检而妥协"反向污染产物。** 修法是让**前端与契约走同一个 `_norm_path`**，统一处理 `${id}` / `{id}` / `:id` 三种写法，比对口径一致后误判消失。

### 5.7 "全绿但功能缺失"：补一个覆盖率检查

5.6 修好越界误判后，又发现新问题：QA 只检查"有没有越界调用"，却不检查"有没有漏做操作"。于是 `app.js` 只做增/查、丢掉删/改也能全绿。新增 `_check_frontend_coverage`：按 HTTP 方法粒度**反向核对**——契约里出现的每种方法（GET/POST/PUT/DELETE/PATCH），前端代码里都得有对应的 `fetch` 调用，否则判定"对应功能没做"。"不越界"和"不漏做"这才凑成双向约束。

### 5.8 "语法对但跑不起来"：补运行时冒烟 + DOCTYPE + 静态托管

`node --check` 全过，项目却可能：启动即崩溃；或缺 `express.static`，访问 `/` 直接 `Cannot GET /`；或 `index.html` 第一行写成 `<!--DOCTYPE`（漏感叹号）被当注释、整页解析异常。这些都是"语法层看不出、一跑才现形"的问题。对策是三个检查叠加：**运行时冒烟测试**（4.2，真跑真打接口）、**`<!DOCTYPE html>` 前缀检查**、**`express.static` 正则检查**。冒烟测试是其中的治本兜底——它是唯一能模拟真实用户访问、把"能不能跑起来"变成可判定信号的手段。

### 5.9 跨平台细节：Windows 解码崩溃、`npm.cmd`、随机端口

- **Windows GBK 解码崩溃**：早期对 `node --check` 的子进程用了 `text=True`，它按系统 locale（Windows 上是 GBK）解码 node 的 UTF-8 输出，遇到非 ASCII 直接抛 `UnicodeDecodeError`，导致 `stderr=None` 后续崩溃。改为显式 `encoding='utf-8', errors='replace'` 并对 `stderr/stdout` 做 `None` 防御。
- **`npm` 在 Windows 上是 `npm.cmd`**：`runner.py` 统一用 `shell=True` 调用固定字面量命令（`cwd` 为受信任的项目目录），三平台通吃。
- **冒烟测试用随机空闲端口**：先 `bind(("127.0.0.1", 0))` 让 OS 分配端口再释放，避免与本机已占用端口冲突。

### 5.10 区分"可重试"与"致命"错误，少走 3 次弯路

`chat_json` 的重试一开始是无脑重试。但 404（`LLM_BASE_URL` 没加 `/v1`）、401（key 无效）、连接拒绝（服务没起）这类是**配置/环境错误**，重试 3 次只是把同一个错误重复 3 遍、白等。改为：只对 `JSONDecodeError` 带着错误反馈重试（让模型自我修正格式），其余 `Exception` 立即抛出，并附上当前 `base_url` / `model` 和常见修复建议（如 Ollama 要用 `http://localhost:11434/v1`）。把"该重试的"和"该报错的"分开，定位问题快得多。

### 6.1 关键模块详解

**BaseAgent（基类）**：封装所有 Agent 共用逻辑——LLM 调用、prompt 落盘、产物落盘、日志。具体 Agent 只需实现 `system_prompt()` 和 `run()`，保持良好的开闭原则。

**LLMClient**：统一封装 OpenAI 兼容接口，支持 DeepSeek / 智谱 / Kimi / OpenAI / 本地 Ollama 等，通过 `.env` 切换、代码不改。核心是 `chat_json()`：JSON Mode + 失败重试（错误分级，见 5.10）+ 去代码围栏兜底。

**SharedContext**：黑板。集中管理中间产物、负责落盘、提供 `summary_for()` 上下文裁剪与 `qa_failures` 的注入/清空。

**Orchestrator**：流水线编排器，系统的"指挥官"。决定 Agent 执行顺序、管理人工介入点、驱动 **QA 自动修复循环**（含失败项→Agent 的映射逻辑 `_get_failed_agents`），最终落盘、汇报、并按需自动启动。

**QAAgent**：质量刹车。10 项确定性检查 + 运行时冒烟，详见第四章。

**runner.py（新增）**：QA 通过且 `--run`/`AUTO_RUN=true` 时，自动 `npm install`，延迟 2.5s 开浏览器（给 server 留启动时间），再前台 `npm start`，阻塞至 Ctrl+C。无 node/npm 时优雅跳过并给出手动命令。

## 八、Future Work

初稿列出的「Fix Loop（自动修复循环）」和「端到端运行测试」在本版已落地（见 4.2、4.3）。后续可继续迭代的方向：

1. **Backend / Frontend 并行执行**：因为下游只依赖契约、不读上游代码（见 3.3），二者并行在正确性上已无障碍，可缩短总耗时。需要处理日志交错与产物写入顺序。
2. **更智能的修复定位**：当前失败项→Agent 是基于检查名的规则映射。可让冒烟测试回传更结构化的失败原因（哪个接口、什么 5xx），让修复 prompt 更精准，减少修复轮数。
3. **更大上下文 / 更强模型的弹性配置**：当受限于本地小模型用了 8k 窗口（见 5.2）。可让 `summary_for()` 根据模型窗口大小自适应——窗口大时可附带更多上下文（如上游代码片段）以提质，窗口小则继续走极简策略。
4. **可选技术栈**：当前固定 Node + Express + JSON 文件。可扩展为用户可选（如需要并发/查询时切回真正的数据库，或换 Python/FastAPI 后端）。
5. **多轮增量迭代**：支持用户对已生成项目提修改意见，Agent 团队在现有产物上**增量更新**而非整体重生成。
6. **更丰富的冒烟覆盖**：当前只打"第一个集合级 GET + 第一个 POST"。可扩展为遍历契约全部接口、并对 PUT/DELETE/PATCH 做"先建后改/删"的链式断言。
